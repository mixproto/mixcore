# X32 / M32 network control protocol (as implemented by mixcore)

Scope: Behringer X32 family and Midas M32 family consoles (compatibility statement only; mixcore is not affiliated
with or endorsed by any console maker). This file lists the protocol facts that `driver/x32` and `sim/x32` implement.
The driver and the simulator are both written from this file, never from each other. When a real console disagrees
with this file, the console wins: record a `[CAPTURE]` fact here first, then change the simulator, then the driver.

## Tags
- `[OFFICIAL]` a document published or authorised by the manufacturer, or a formal specification.
- `[CODE]` behaviour confirmed by reading permissively licensed source code (MIT/BSD/Apache).
- `[COMMUNITY]` a community write-up (here mostly the unofficial reference PDF below).
- `[CAPTURE]` our own packet capture from real hardware. **None yet: no hardware was available for this spike.**
- `[UNVERIFIED]` plausible, not confirmed by any of the above. Every such fact is a simulator option.

## Facts

### Transport and encoding
| ID | Fact | Source |
|---|---|---|
| X32-F01 | Control runs over UDP. The console listens on port **10023** and sends every reply to the IP address and port the request came from. | S1 p.5 `[COMMUNITY]`; S2 `src/main.ts` uses remote port 10023 `[CODE]` |
| X32-F02 | Packets are plain OSC 1.0 messages: big-endian, 4-byte aligned, NUL-padded strings, types `i` (int32), `f` (float32), `s` (string), `b` (blob). We never send bundles. | S1 p.10 `[COMMUNITY]`; S3 `[OFFICIAL]` |
| X32-F03 | A request may carry an empty type tag string (`/info` + `,`) or omit it entirely (older OSC form); both are accepted by the console. mixcore sends the empty tag form. | S1 p.10 `[COMMUNITY]` |
| X32-F04 | Reading a parameter: send its address with no arguments; the console answers with the same address and the current value. | S1 p.7 `[COMMUNITY]` |
| X32-F05 | Writing a parameter: send its address with one argument of the parameter's type. The console applies values that exist and are in range. It sends no acknowledgement to the writer. What it does with an out-of-range or wrongly typed value is not documented `[UNVERIFIED]`; mixcore never sends one (values are clamped and typed in the driver). | S1 p.7 `[COMMUNITY]` |
| X32-F06 | An unknown address gets no reply `[UNVERIFIED]`. | none |
| X32-F07 | Over a slow Wi-Fi link the console can send faster than the access point forwards, and UDP drops packets silently. Large bursts of requests should be paced. mixcore keeps at most 16 reads in flight during the initial read and retries reads that got no answer (a read is never a write). | S1 p.5 `[COMMUNITY]`; window size is our design choice |

### Subscriptions, echo and liveness
| ID | Fact | Source |
|---|---|---|
| X32-F20 | `/xremote` (no arguments) asks the console to push parameter changes to the sender for **10 seconds**. The client must send it again before that time runs out. | S1 p.8 `[COMMUNITY]` |
| X32-F21 | Pushes go to at most **four** active `/xremote` clients. Other clients can still read and write but get no pushes. Which client loses when a fifth one registers is not documented `[UNVERIFIED]`; the simulator default ignores the newcomer until a slot expires, and the opposite policy (evict the oldest) is an option. | S1 p.8 `[COMMUNITY]` |
| X32-F22 | A push carries changes made on the console surface or by **another** client, in the same form as a read reply (address + value). | S1 p.9 `[COMMUNITY]` |
| X32-F23 | The console does **not** push a change back to the client that sent it. Companion therefore sends writes from a second UDP socket, so the socket that holds `/xremote` sees its own writes as changes from "another client". mixcore does the same: one socket for `/xremote`, reads and meters, one socket for writes only. Whether the write socket counts against the four-client limit is `[UNVERIFIED]` (it never sends `/xremote`, so we expect not; see X32-F28 and "Sockets of a mixcore session" below). | S2 `src/main.ts` (comment above `oscSend`) `[CODE]`; consistent with X32-F22 |
| X32-F24 | Whether the console pushes a write that sets a parameter to the value it already has is `[UNVERIFIED]`. mixcore does not rely on it. | none |
| X32-F25 | The protocol has no heartbeat, and `/xremote` only pushes changes, so a quiet console sends nothing. Companion polls `/xinfo` and treats a missing reply within 5 s as a lost console. mixcore counts **every** packet from the console (reply, push, meter, re-read reply) as proof that the downlink works, sends `/xinfo` whenever nothing arrived for 400 ms (quiet probe), and declares the console lost after **1.5 s without any packet** (design rule SR-05/CR-06, our choice). Pushes and meters do not prove that our own packets reach the console (they keep coming for up to 10 s after the uplink dies), so mixcore also sends one `/xinfo` per second and declares the console lost after 3 s without an `/xinfo` reply. All intervals are design targets. | S2 `src/main.ts` `pulse()` `[CODE]`; S1 p.8 (10 s lifetime) `[COMMUNITY]` |
| X32-F26 | After a console reboot all `/xremote` and `/meters` registrations are gone `[UNVERIFIED]` (they are not part of a scene or a setting). mixcore re-registers and re-reads the whole state after every reconnect anyway. | none |
| X32-F27 | Renewal interval chosen by mixcore: every 3 s (at most a third of the 10 s lifetime, so two renewals can be lost). Companion uses 1.5 s. | S2 `src/main.ts` `[CODE]`; interval is our design choice |
| X32-F28 | The console tells clients apart by source IP address **and port**: replies and pushes go to the port a request came from, and a socket with a new source port is a new client. A `/xremote` registration from an abandoned port keeps its slot until its 10 s run out, so a client that opens new sockets on every retry can fill the four slots and starve itself and other apps (one bridge saw an already connected client flap 19 times until it reused one socket). Whether a port that never sent `/xremote` (reads and writes only) also takes a slot is `[UNVERIFIED]`. | S1 p.5-6 (reply to the requester's port) `[COMMUNITY]`; S7 (field report) `[COMMUNITY]` |
| X32-F29 | A client beyond the push limit can still read and write; it just gets no pushes (one field report: four apps fully synced, a fifth could send but never synced). The console sends nothing that says "you are not served". Forum posts that claim 10 or 16 clients contradict S1 `[UNVERIFIED]`; mixcore keeps 4. | S1 p.8 `[COMMUNITY]`; S8 `[UNVERIFIED]` |

#### Sockets of a mixcore session (resolves X32-F23 against X32-F28)
- mixcore opens its two UDP sockets **once per engine session** (from `Start` to `Stop`) and keeps them through every
  reconnect, every `Pause`/`Resume` and every background re-read. A socket is reopened only after it failed (the OS
  reported an error on it); that is logged at Info. So the source ports never change while a console is in use.
- The two-socket design of X32-F23 stays: the evidence for it (S2: the console does not push a change to its sender)
  is code we can read, and without it we could not tell a confirmed write from a lost one. The cost is bounded: the
  subscription socket takes one `/xremote` slot; the write socket never sends `/xremote`, so under the documented
  model (S1) it takes none, and under the pessimistic reading of X32-F28 it takes one more, constant across
  reconnects. `cmd/mixprobe` measures which one is true on hardware (to-verify item 2).
- The simulator models the slot table as described: every port that sent `/xremote` holds a slot for 10 s, at most
  four, and an option (`SlotForAnySender`) makes every sending port take a slot (the pessimistic reading).

#### Client limit detection in mixcore (design, built on X32-F21, X32-F23, X32-F29)
The console gives no signal, so mixcore infers "our `/xremote` is not served" (state `limited`) from two pieces of
evidence, both while `/xinfo` replies prove the console is alive:
- three writes of ours that changed a channel value (fader, mute, name) got no echo on the subscription socket within
  the echo window (2 s), and no push of any kind arrived meanwhile (a write that sets the value the console already has
  is not counted, X32-F24; mute group and DCA writes do not count until hardware confirms they are pushed);
- two background re-read passes in a row each found a value that changed without a push, and no push arrived meanwhile.
Any push on the subscription socket clears `limited` and starts a background re-read (changes made meanwhile were
never pushed). A reconnect starts unlimited. There is no polling fallback
(design CR-15 is unverified): while limited, values may be stale and input is locked.

### Parameters used by this driver
| ID | Fact | Source |
|---|---|---|
| X32-F30 | Input channels are `01`..`32`, always written with two digits: `/ch/01/...` to `/ch/32/...`. | S1 p.24 `[COMMUNITY]` |
| X32-F31 | `/ch/NN/config/name` is a string of at most 12 characters. Which characters the console accepts beyond plain ASCII is `[UNVERIFIED]`; mixcore writes printable ASCII only. | S1 p.24 `[COMMUNITY]` |
| X32-F32 | `/ch/NN/mix/fader` and `/main/st/mix/fader` are "level" floats from 0.0 to 1.0 (fader law below). | S1 p.25, p.35 `[COMMUNITY]` |
| X32-F33 | `/ch/NN/mix/on` and `/main/st/mix/on` are an int: **1 = on (not muted), 0 = off (muted)**. The mute button of the console is the inverse of this switch. | S1 p.25, p.35 `[COMMUNITY]`; S2 `src/choices.ts` `CHOICES_MUTE` (mute = 0, unmute = 1) `[CODE]` |
| X32-F34 | `/main/st` is the main stereo (LR) bus. | S1 p.34 `[COMMUNITY]`; S2 `src/paths.ts` `[CODE]` |
| X32-F35 | Six mute groups: `/config/mute/1` .. `/config/mute/6`, an int. **1 = group engaged (its members are muted), 0 = released**: the opposite polarity of a channel's `mix/on`. There is no toggle command; a toggle is "read the state, write the inverse". Groups have no names on the console. Changes are pushed to `/xremote` clients like any parameter (the surface's mute group buttons generate `/config/mute/N`). | S5 sec. 5.8 (six groups) `[OFFICIAL]`; S1 p.21, p.130 `[COMMUNITY]`; S2 `src/feedback.ts` (group "muted" when the value is 1) `[CODE]` |
| X32-F36 | Mute group membership of a strip: `<strip>/grp/mute`, an int bitmap 0..63 where bit n-1 set means "member of group n". mixcore reads it on `/ch/01..32` and `/main/st`. | S1 p.27, p.36 `[COMMUNITY]`; S4 `BitSet` (`1 << (n-1)`) `[CODE]` |
| X32-F37 | Eight DCA groups. `/dca/1..8/on` is an int with the channel polarity: **0 = DCA muted**, 1 = on. (One diagram in S1 draws `/dca/N/mix/on`; the parameter tables and both code sources use `/dca/N/on`, so mixcore does.) | S1 p.39 `[COMMUNITY]`; S2 `src/paths.ts`, S4 `DcaNode` `[CODE]` |
| X32-F38 | DCA membership of a strip: `<strip>/grp/dca`, an int bitmap 0..255, bit d-1 = member of DCA d. mixcore reads it on `/ch/01..32`. | S1 p.27 `[COMMUNITY]`; S4 `[CODE]` |
| X32-F39 | A muted DCA silences its members toward Main LR. Toward the mix buses it does so only when the preference `/-prefs/dcamute` is ON (default OFF), so monitor sends stay live by default `[UNVERIFIED]`. With `/-prefs/hardmute` OFF (default) a channel muted by its own button is said to follow a group's release; with ON only its own button unmutes it `[UNVERIFIED]`, contradicting the plain "OR" description of S6. mixcore computes the **effective mute toward Main LR** as own mute OR any engaged member mute group OR any muted member DCA, and reads neither preference: if the console itself rewrites `mix/on` when a group changes, the pushes keep the own mute right. Per-bus effective mute comes with buses. | S6 `[COMMUNITY]`; S1 p.57 (preference names) `[COMMUNITY]` |

### Scene recall
| ID | Fact | Source |
|---|---|---|
| X32-F60 | There is **no dedicated scene-recall event**. A recall at the desk reaches `/xremote` clients as pushes of the parameters it changed, i.e. a burst of pushes; the surface appendix lists `/-undo/time` among the messages of the scenes section. Whether `/-undo/time` or `/-show/prepos/current` is actually pushed on a recall is `[UNVERIFIED]`. | S1 p.130 `[COMMUNITY]` |
| X32-F61 | `/-show/prepos/current` (int) is the cue, scene or snippet **highlighted** on the console's scenes page (which kind depends on `/-prefs/show_control`), not "the last scene loaded"; it can move without anything being loaded. | S1 p.45, p.57 `[COMMUNITY]`; S2 `src/actions/go-command.ts` `[CODE]` |
| X32-F62 | `/-undo/time` (string) is the time of the console's single undo checkpoint, which a scene recall sets. | S1 p.70, p.72, p.130 `[COMMUNITY]` |

mixcore's scene-recall heuristic (event `sceneRecalledAtConsole`, design): signals are (a) a **burst**, at least 8
different parameters pushed from the console within 250 ms, (b) a push of `/-undo/time`. A push of
`/-show/prepos/current` is only a hint: it moves while the engineer browses the scene list (X32-F61), so it never
raises an event alone; when it came within 1 s of a recall its value is reported as the highlighted scene, never as
"the loaded scene". Confidence is `high` for a burst with (b), `medium` for (b) alone, `low` for a burst alone. Our own echoes never count;
another app changing many parameters at once looks like a `low` recall. The event is reported once its signals settle
(250 ms without a new one, at most 1 s after the first). Every held fader ends as
an external change and a read-only background re-read starts at once (a burst over Wi-Fi can lose packets). mixcore
does not read either address at connect, so a console that does not know them costs nothing.

### Fader law (level type)
| ID | Fact | Source |
|---|---|---|
| X32-F40 | The 0.0..1.0 float maps to dB in four straight segments: 0.5..1.0 is -10..+10 dB (dB = 40f - 30); 0.25..0.5 is -30..-10 dB (dB = 80f - 50); 0.0625..0.25 is -60..-30 dB (dB = 160f - 70); 0.0..0.0625 is -90..-60 dB (dB = 480f - 90). The inverse uses the same segments. | S1 p.9 (type table) and p.131 (conversion appendix) `[COMMUNITY]`; S2 `src/util.ts` `floatToDB`/`dbToFloat` `[CODE]` |
| X32-F41 | The console knows **1024 steps**: the valid values are k/1023 for k = 0..1023, and other floats are rounded to the nearest known step. The appendix also prints a rounding formula, `int(f * 1023.5) / 1023`, but it lands one step low at some points (0.25, the -30 dB break, becomes step 255, while the 1024-entry table puts -30 dB at step 256), so mixcore rounds to the nearest step, k = round(f * 1023). | S1 p.12 (rounding to known values), p.131, p.146 (1024-entry table) `[COMMUNITY]`; the step-255 example is checked in `driver/x32/convert_test.go` |
| X32-F42 | Step 0 (0.0) is shown as **-oo** (off) in the table; step 1 (about 0.0010) is -89.5 dB. A note says the console may use -144 dB internally for -oo, but no reported value shows it. mixcore maps 0.0 to -inf and anything at or below -90 dB to 0.0. Confirm on hardware `[UNVERIFIED]`. | S1 p.131 footnote, p.146 `[COMMUNITY]` |
| X32-F43 | Worked example: the PDF's fader packet `2f63682f30312f6d69782f6661646572000000002c6600003f5334cd` (`/ch/01/mix/fader ,f`) carries `0x3f5334cd` = 0.8250244 = step 844 of 1023, which is +3.0 dB. Unity (0 dB) is 0.75. | S1 p.12 `[COMMUNITY]`; arithmetic checked in `driver/x32/convert_test.go` |

| ID | Fact | Source |
|---|---|---|
| X32-F50 | `/meters ,s <bank>` (plus optional ints) starts a meter stream for **10 s**; it must be re-sent to continue. The default interval is 50 ms. An optional last int `time_factor` in 1..99 multiplies the interval; values outside that range act as 1. | S1 p.7, p.15 `[COMMUNITY]` |
| X32-F51 | Bank `/meters/1` returns 96 values per packet: 32 input channels, then 32 gate gain reductions, then 32 dynamics gain reductions. mixcore uses only the first 32 (input channels 1..32). | X32-F52 | The bank string appears in two forms in S1: `meters/1` (command table, p.7) and `/meters/6` (meter chapter example, p.15). mixcore sends the slashed form `/meters/1` `[UNVERIFIED]` which form the console requires; the simulator accepts both. | S1 p.7, p.15 `[COMMUNITY]` |
| X32-F53 | A meter packet is an OSC message whose address is the bank (e.g. `/meters/1`) with one blob argument. | X32-F54 | Meter values are linear amplitude: 1.0 is 0 dBFS and the console can report up to 8.0 (+18 dBFS). mixcore converts to dBFS with 20*log10(v); 0 or less becomes -inf. | S1 p.15 `[COMMUNITY]` |

Same blob layout, scaling, rate and lifetime as bank 1 (X32-F50, X32-F53, X32-F54). mixcore uses only Main L/R. | S1 p.17-18 `[COMMUNITY]` |

## Echo and conflict handling in mixcore (required by our safety rules)
- Our writes leave from the write socket; the console pushes them to the `/xremote` socket (X32-F22, X32-F23). The
  driver remembers the last value it wrote per parameter for 2 s; a push with the same value inside that window is
  reported as the echo of that write (same origin and sequence number), not as a console change. Nothing in the driver
  or the supervisor ever writes in response to a push, so an echo cannot bounce.
- The driver keeps the last 32 written values per parameter for that match, so the echo of an early write in a fast
  drag is not mistaken for a desk change.
- While a person holds a fader, an external change of it (a desk move, a scene recall or another client's write) is
  published at once and ends that person's gesture; their further writes to that fader are refused until they touch
  it again. Losing the console cancels every hold. Our own echo never ends a gesture. A desk move to exactly the value
  we wrote within the 2 s window is indistinguishable from our echo (accepted limitation).
- Capability `EchoesOwnWrites` is reported as true because of the two-socket scheme.

## Background re-read (lost pushes)
UDP drops packets silently (X32-F07), so a push can be lost and the shown value would stay wrong until the next change.
While live, the supervisor asks the driver every 15 s for one read-only pass over every parameter, skipped while any
fader is held. The driver:
- sends the reads (X32-F04) in batches of 16 per `/xinfo` poll interval, so a pass is paced like the initial read and
  takes about 6 s;
- sends them from the **write socket**, which never sends `/xremote` and therefore receives replies but no pushes
  (X32-F01, X32-F21): a reply can never be mistaken for a push or for the echo of our own write;
- skips a parameter written by us within the echo window, and drops a reply when one of our writes or a push of that
  parameter arrived after the read was sent, so an older value can never replace a newer one;
- reports only a value that differs from the newest one seen, as a console change. That change ends a hold like any
  other external change, which is correct: the desk did move it.
Late replies (after the next batch) are dropped. A pass never writes.

2. X32-F23: the write socket does not count against the four-client limit; the console pushes our writes to our
   `/xremote` socket.

4. X32-F26: subscriptions are dropped by a reboot.
5. X32-F31: characters accepted in names.

8. X32-F05/F06: behaviour on unknown addresses and out-of-range values.
9. X32-F01/F21: reads sent from the write socket (no `/xremote`) are answered to that socket; the background re-read
   relies on it.
10. X32-F28: a port that never sent `/xremote` takes a slot or not (decides whether a mixcore session costs one slot or
    two); slot usage stays constant across 20 reconnects.
11. X32-F25: a quiet console answers every quiet `/xinfo` probe, so the 1.5 s stale timer never fires on a healthy link.
12. X32-F35..F38: the addresses answer reads; `/config/mute/N` = 1 means engaged; group engage does not rewrite the
    members' `mix/on` (OR model).
13. X32-F39: DCA mute toward buses with `/-prefs/dcamute` OFF and ON; hard-mute semantics.
14. X32-F60..F62: what a desk scene recall pushes (burst size and duration, `/-undo/time`, `/-show/prepos/current`).
15. X32-F55: bank `/meters/2` count and the Main L/R positions; meter interval 50 ms and 10 s lifetime (X32-F50).

`cmd/mixprobe` checks items 1, 2, 3, 6, 7, 9-12, 14 and 15 on a real console in one guided session (`go run
./cmd/mixprobe --lab -host <ip>`, report in `mixprobe-<time>/report.md`). Item 4 cannot be told apart from the 10 s
expiry (a boot takes longer), so mixprobe only measures the recovery; items 5, 8 and 13 need a person to look at the
console or listen and stay manual.
