# Shared gesture-path fixtures (CR-27, redesign CC-8)

`gesture-paths.json` holds the touch paths of `dybyskz-mix/docs/design/acceptance/phone-safety.md` ("Touch paths") and,
since core-api v0.5, the Gain wheel paths of `acceptance/redesign.md` (AC-RD-G01, AC-RD-G02) as data, so the core's
tests, each UI's gesture-machine unit tests and the device UI tests replay exactly the same points. It is generated by
`api/gesturepaths_test.go` (`go test ./api -run GesturePaths -args -update-paths`); a test fails when the file and the
generator differ.

Format: `paths[]` with `id`, `motion`, `why`, `largeContact` (true: the contact is larger than `touch.largeContact`, it
must never grab), optional `start` and `pointer` (v0.5), and `variants[]`. A variant has an `orientation` (`any`,
`portrait`, `landscape`; P2 and P6 differ by the control's length) and `points[]` of `{t, x, y}`: `t` in ms since
touch-down, `x` and `y` in pt (Apple) or dp (Android) relative to the touch-down point, `+x` right and `+y` up (screen
directions), one point every 8 ms. The finger (or mouse button) lifts after the last point.

- **P1..P8, P1D** start on the control (a fader cap or the Gain wheel); **P1R..P6R** are P1..P6 rotated 90 degrees
  clockwise (up becomes right).
- **v0.5 removed P9 and P10**, the slip-guard climb and rest paths (SR-26 retired, CC-1).
- **v0.5 Gain row paths** carry `start`: `{"control": "gainWheel", "fromLeftPt": n}` starts n pt inside the wheel's left
  end (absent `fromLeftPt`: the wheel's centre); `{"control": "screenEdge", "edge": "left" | "right", "fromEdgePt": n}`
  starts n pt off that screen edge, where only the `-1` / `+1` steppers are (SR-32). `pointer: "mouse"` is a mouse drag
  with the button held.
  - G1: from 5 pt inside the left end, right 230 at 750 pt/s (AC-RD-G01: four 1 dB writes on a 240 pt wheel).
  - G2, G2D, G2M: from the centre beyond the frame, straight, with a 40 pt drift, and with the mouse there and back
    (AC-RD-G02: the stroke ends at the frame, coming back writes nothing).
  - G3: the longest stroke on the iPhone 6.1" portrait wheel, 1 pt inside one end to 1 pt inside the other (238 pt).
  - E10L..E40L, E10R..E40R: back swipes on the Gain row from 10, 20, 30 and 40 pt off each screen edge, 200 inward in
    150 ms (zero Gain writes).

What the core proves with it (`api/gestureproof_test.go`), through a double of the UI gesture machine (relative, one
locked axis, constant ratio, `gesture.lockAxis` 10, `gain.encoderPitch` 48, the wheel's frame rule with
`gain.wheel.frameSlop` 16) and the real engine against the X Air simulator, on iPhone 6.1" geometry (fader track 490 /
152 pt, Gain wheel 240 / 191 pt, 76 pt from each screen edge in portrait): AC-PS-01 as amended and AC-RD-F01 (every fader
path follows the finger on the law, P2 reaches +10 dB without a stop), AC-PS-02 and AC-PS-06 as amended (vertical paths
never write Gain; a path changes Gain by at most floor(half the wheel / 48) dB; the legacy absolute, angle and
speed-up doubles still reach the range maximum), AC-RD-G01 and AC-RD-G02 (the Gain row paths). The core does not cap a
stroke: the frame rule lives in each UI, and the core bounds each write (SR-31, core-api README rule 8).
