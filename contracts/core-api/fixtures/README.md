# Shared gesture-path fixtures (CR-27)

`gesture-paths.json` holds the touch paths of `dybyskz-mix/docs/design/acceptance/phone-safety.md` ("Touch paths") as
data, so the core's limiter tests, each UI's gesture-machine unit tests and the device UI tests replay exactly the same
points. It is generated by `api/gesturepaths_test.go` (`go test ./api -run GesturePaths -args -update-paths`); a test
fails when the file and the generator differ.

Format: `paths[]` with `id` (P1..P8, P1D, P1R..P6R, and P9: five 40 pt climbs each followed by a 400 ms rest, a
deliberate climb that opens several slip-guard walls in one gesture; its writes must never fall; P10: a move past the
first wall, a 1000 ms rest with a +-3 pt sway at 1.5 Hz (below `wall.restSpeed`), then up again; the wall must open
in portrait and landscape and the value follow the finger without a jump; the UI sends `trackLengthPt` with
`holdBegin`), `motion`, `why`, `largeContact` (true: the contact is larger than
`touch.largeContact`, it must never grab) and `variants[]`. A variant has an `orientation` (`any`, `portrait`,
`landscape`; P2, P6 and P10 differ by the control's length) and `points[]` of `{t, x, y}`: `t` in ms since touch-down, `x`
and `y` in pt (Apple) or dp (Android) relative to the grab point, `+x` right and `+y` up (screen directions), one point
every 8 ms. The finger lifts after the last point. P1R..P6R are P1..P6 rotated 90 degrees clockwise (up becomes right).

What the core proves with it (`api/gestureproof_test.go`): through a double of the UI gesture machine (relative, one
locked axis, constant ratio, `gesture.lockAxis` 10, `gain.encoderPitch` 48, `wall.dwell` 300 ms below
`wall.restSpeed` 30 pt/s) and the real engine against the X Air simulator, on iPhone 6.1" geometry (fader track 490 /
152 pt, Gain bar 361 / 343 pt): AC-PS-01 (fader), AC-PS-02, 03 and 05 (Gain) and AC-PS-06 (the absolute, angle and
diagonal speed-up doubles reach the range maximum on P2, P5 and P4; ours on no path).
